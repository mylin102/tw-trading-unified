# Runbook Authoring Rules

這份規則把「快照是手段，不是步驟」固定成可檢查的 repo 合約。

## 規則

1. `## 階段 N` 只列可執行動作：會改變狀態，或有明確 return code（RC）的檢查。不得把檔案、快照或報告本身當成階段。
2. 產物（快照、證據、hash、報告、備份）集中放在 `〈產物〉` 節，欄位固定為：產物 | 何時產生 | 命令 | 落點。
3. 產物不得有階段編號，不得寫成「先抓一份放著」；它是動作的輸出或輸入契約。
4. 每個產物的消費端必須聲明新鮮度需求。例如：與使用相隔超過 10 分鐘，必須重抓；跨 session 或來源變更也必須重抓。
5. 每個階段必須有驗收/RC 判斷點，明確寫出 PASS/FAIL、RC 或停止條件。

## 正確與錯誤對照

正確：階段先執行「驗證 deployment gate 並在失敗時停止」，其輸出的 gate 證據列在 `〈產物〉`，並由消費端聲明 10 分鐘新鮮度。

錯誤：把本次 runbook 的「階段 1：收集 gate 所需證據」當作階段。這會把快照/證據這個手段誤升格成流程步驟，且沒有說明誰消費、何時失效。

### 〈產物〉

所有 runbook 若提及 snapshot、capture、evidence、hash、報告或備份，都必須有此節，並使用下列欄位。

| 產物 | 何時產生 | 命令 | 落點 |
|---|---|---|---|
| gate snapshot / evidence | 執行 gate 動作時 | `<command>` | `<path>` |
